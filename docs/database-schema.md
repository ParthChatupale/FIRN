# FIRN Database Schema

This document describes the simulation schema (`0001_simulation_runs`), Phase 5 plan workflow (`0002_plan_management`), and Phase 6 monitoring workflow (`0003_monitoring_replanning`). The local application database `firn_db` remains at `0002_plan_management`; the isolated `firn_test_db` is the target for testing the new additive migration. This is still not FIRN's final operational/digital-twin schema.

The schema persists complete simulation runs and their hourly telemetry. Simulation calculations remain in the existing simulator; the database stores inputs and outputs so a run can be listed and inspected later.

## Relationship

```text
simulation_runs (one) ────────< simulation_telemetry (many)
         id                              (run_id, hour)
```

Deleting a run cascades to its telemetry rows. Each telemetry hour is unique within a run.

## `simulation_runs`

One row represents one completed simulation run.

| Column | PostgreSQL type | Null? | Key / default | Purpose |
|---|---|---:|---|---|
| `id` | `UUID` | No | Primary key; generated by the application | Stable identifier for API access |
| `scenario` | `VARCHAR(40)` | No | Indexed | Scenario name, e.g. `normal`, `storm`, or `generator_failure` |
| `station_name` | `VARCHAR(160)` | No | — | Station the simulation represents |
| `duration_days` | `INTEGER` | No | — | Simulated duration in days |
| `seed` | `BIGINT` | No | — | Random seed, preserving repeatability across the API's signed 64-bit range |
| `simulator_version` | `VARCHAR(32)` | No | — | Version identifier for the simulation logic used |
| `started_at` | `TIMESTAMP WITH TIME ZONE` | No | — | Simulated start instant |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | No | Database default `now()`; indexed | When this record was inserted |
| `config_snapshot` | `JSONB` | No | — | Inputs/configuration captured for this run |
| `summary` | `JSONB` | No | — | Aggregate outcome and key metrics |
| `mission_results` | `JSONB` | No | — | Per-mission outcomes and metrics |
| `event_log` | `JSONB` | No | — | Events generated during the run |

Indexes:

- `ix_simulation_runs_scenario` on `scenario`
- `ix_simulation_runs_created_at` on `created_at`

## `simulation_telemetry`

One row represents one hourly telemetry sample for a run.

| Column | PostgreSQL type | Null? | Key / default | Purpose |
|---|---|---:|---|---|
| `run_id` | `UUID` | No | Part of primary key; foreign key to `simulation_runs.id`, `ON DELETE CASCADE` | Owning run |
| `hour` | `INTEGER` | No | Part of primary key | Hour offset within the run |
| `payload` | `JSONB` | No | — | Telemetry values for that hour (energy, fuel, weather, assets, and other simulator outputs) |

Primary key: (`run_id`, `hour`). This both prevents duplicate hourly samples for a run and supports reading a run's telemetry in hour order.

## Phase 5: `plan_versions` and `plan_events`

Revision `0002_plan_management` adds two tables without altering existing simulation rows:

### `plan_versions`

One row is one immutable candidate version. Lifecycle state is mutable, but source settings, solver/model provenance, plan payload, and explanations are immutable; an operator edit inserts a child version instead.

| Column | PostgreSQL type | Null? | Key / default | Purpose |
|---|---|---:|---|---|
| `id` | `UUID` | No | Primary key; application generated | Version identifier |
| `plan_group_id` | `UUID` | No | Indexed; groups a lineage | Stable plan lineage |
| `version_number` | `INTEGER` | No | Unique with `plan_group_id`; > 0 | Ordered version within lineage |
| `parent_version_id` | `UUID` | Yes | Self FK, `ON DELETE RESTRICT` | Previous version for an operator-edited branch |
| `source_simulation_run_id` | `UUID` | Yes | FK to `simulation_runs`, `ON DELETE RESTRICT` | Matched simulation context, if provided |
| `station_name` | `VARCHAR(160)` | No | Indexed | Station identity used by this prototype |
| `scenario` | `VARCHAR(40)` | No | — | Synthetic scenario name |
| `days`, `seed`, `flexibility_hours` | `INTEGER`, `BIGINT`, `INTEGER` | No | Duration > 0 | Reproduction/planning settings |
| `simulation_start_time` | `VARCHAR(64)` | No | — | Time origin used for optimizer replay |
| `solver_name` | `VARCHAR(64)` | No | — | Solver reported for the plan |
| `solver_version` | `VARCHAR(32)` | No | — | Installed solver package version |
| `planner_model_version` | `VARCHAR(64)` | No | — | FIRN formulation identifier |
| `status` | `VARCHAR(16)` | No | Indexed; constrained lifecycle values | Current workflow state |
| `plan_snapshot` | `JSONB` | No | — | Schedule, dispatch, trajectories, objectives, assumptions, replay and solver result |
| `explanations` | `JSONB` | No | — | Mission decisions, limit evidence, and replay outcome metrics |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | No | Database default `now()`; indexed | Version creation time |

There is a unique constraint on (`plan_group_id`, `version_number`) and a PostgreSQL partial unique index on `station_name` for rows with `status = 'active'`, enforcing at most one active plan per station name. Status values are `proposed`, `reviewed`, `approved`, `active`, `superseded`, and `rejected`.

### `plan_events`

One append-only row records a proposal creation, edit, review, approval, rejection, activation, or supersession. It stores the owning version ID, action, before/after status, caller-supplied actor label, optional note, JSONB details, and database creation time. Updating or deleting events through the ORM is rejected. Authentication is not part of this phase, so `actor` is not verified identity.

## Phase 6: `monitoring_sessions` and `monitoring_events`

Revision `0003_monitoring_replanning` adds a persisted playback clock and append-only alert/action history. It references existing plan versions and simulation runs; it does not modify their rows or columns.

### `monitoring_sessions`

One row links an active plan to a matching completed simulation run and stores the last consumed telemetry hour, session status, hysteresis state, and any pending proposal. `current_hour = -1` means the simulated clock has not advanced. A session does not activate proposals or replace its active plan.

### `monitoring_events`

One append-only row records a triggered rule, severity, action (proposal, freeze/cooldown/minimum-benefit suppression, or failure), observed metrics, and optional proposed child version. Monitoring JSON captures relevant telemetry and actual-versus-plan values for diagnosis.

## Representative PostgreSQL DDL

The authoritative executable definitions are the Alembic migrations. The SQL below previews the original simulation tables from `0001_simulation_runs` (the UUID primary key's application-side default is not represented as a database default). See `0002_plan_management.py` and `0003_monitoring_replanning.py` for the additive plan and monitor tables.

```sql
CREATE TABLE simulation_runs (
    id UUID PRIMARY KEY,
    scenario VARCHAR(40) NOT NULL,
    station_name VARCHAR(160) NOT NULL,
    duration_days INTEGER NOT NULL,
    seed BIGINT NOT NULL,
    simulator_version VARCHAR(32) NOT NULL,
    started_at TIMESTAMP WITH TIME ZONE NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
    config_snapshot JSONB NOT NULL,
    summary JSONB NOT NULL,
    mission_results JSONB NOT NULL,
    event_log JSONB NOT NULL
);

CREATE INDEX ix_simulation_runs_scenario
    ON simulation_runs (scenario);
CREATE INDEX ix_simulation_runs_created_at
    ON simulation_runs (created_at);

CREATE TABLE simulation_telemetry (
    run_id UUID NOT NULL REFERENCES simulation_runs (id) ON DELETE CASCADE,
    hour INTEGER NOT NULL,
    payload JSONB NOT NULL,
    PRIMARY KEY (run_id, hour)
);
```

## Scope and known boundaries

- This is a persistence schema for simulation runs, not a normalized operational/digital-twin schema for stations, assets, fuel inventory, missions, or observations.
- The current schema has no database `CHECK` constraints for positive duration, valid scenario names, or non-negative telemetry hours; those rules are currently validated by the API/simulator.
- JSONB keeps simulator payloads flexible. Fields inside those documents are not independently indexed or constrained by this migration.
- `id` is generated in the application through SQLAlchemy's UUID default; direct SQL inserts must provide an `id` themselves.
- This initial migration has no downgrade data preservation: downgrading drops both tables and their stored run data.
